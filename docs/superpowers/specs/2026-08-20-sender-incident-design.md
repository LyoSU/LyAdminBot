# Один спамер, багато повідомлень: інцидент відправника

**Дата:** 2026-08-20
**Статус:** затверджений дизайн, до реалізації

## Проблема

Кожне повідомлення судиться так, ніби воно перше. Коли один відправник шле
спалах, це коштує окремого прогону пайплайна (включно з викликом LLM), окремої
картки в чаті, окремого запису у `pipeline_decisions` — на кожне повідомлення.
Вердикт №8 не знає, що вердикт №1 уже забанив цього ж відправника в цьому ж
чаті.

Симетрична прогалина: повторюваність не додає ваги. `adjustSpamMessages` забирає
накопичений standing при enforcement (2026-07-31), тому повтор перестав
*знижувати* score — але й *підвищувати* його не почав.

Що вже є і що НЕ покриває:

- `velocity_repeats` (1.5, evidence) — **однаковий** текст. П'ять різних рядків
  дають п'ять різних хешів `normalizeHeavy` і жодного сигналу.
- `session` / `judgeAccumulated` — лише повідомлення, **занадто короткі** для
  класифікації (`shouldAbstain`), мінімум 5 у вікні, і лише з текстом
  (`text.trim().length === 0` → вихід).
- `applyVerdict` — рівно **один** `messageId`. Спрацювало на шостому — перші
  п'ять лишаються в чаті назавжди.

## Кейси

### Де інцидент допомагає

1. Класика: та сама реклама 6× → 6 вердиктів, 6 карток, 6 викликів моделі.
2. **Спам частинами**: текст → фото → «пиши в ЛС». Кожна частина під планкою,
   разом — очевидний спам. Сьогодні не ловить ніщо.
3. Хвіст після бану: забанили на 3-му, 4–6 уже в черзі → повний прогін за
   користувача, якого в чаті вже немає.
4. Медійний спалах (стікери/фото без тексту): `session` виходить на порожньому
   тексті, abstain теж — не накопичується нічого.

### Де це зробить гірше (і що з цим робимо)

5. Завсідник у суперечці: 8 коротких за 2 хв. Наївне «одне спам → усі спам»
   помножує ціну FP на 8. → Memo не має права судити (див. таблицю повноважень);
   планка C відпускає все, що набрало < 0.35.
6. Учасник вкинув одне посилання, далі звичайна балачка. → Там був `delete`, а не
   виніс людини, тому memo не отримує права видаляти наступні.
7. Чат голосує ham. `restoreFalsePositive` працює на один `messageId` і **не
   вміє відновити видалене**. → Скасування стає інцидент-обізнаним і записує,
   скількох повідомлень коштувала помилка.
8. Сплеск заходів, два різні спамери. → Ключ інциденту `(chatId, userId)`.
9. Спамить у чаті A, нормально говорить у B. → Інцидент не перетинає чати
   (на відміну від `externalBan`, глобального навмисно).

## Дизайн

Три частини на спільному хребті. A не створює нових суджень (тому безризикова),
B створює (тому калібрується), C незворотна (тому має найвужче правило).

### Хребет: `Incident`

`Map<'chatId:userId', Incident>` у процесі бота, TTL 10 хв:

```ts
interface Incident {
  action: VerdictAction        // що вже застосували
  reasonCode: string
  cardMessageId: number | null // картка, яку редагуємо замість надсилання нової
  voteMessageId: number | null // або бюлетень, до якого доліплюємо
  count: number                // скільки повідомлень уже знесено
  removedMessageIds: number[]
  decisionId: string | null    // _id єдиного запису в pipeline_decisions
  openedAt: number
}
```

У пам'яті, не в Mongo — за прикладом `MemoryConversationWindow` і `PendingInput`.
Інцидент живе 10 хвилин, а M0 уже впирався у 512 МБ (чистка 2026-07-06). Ціна
рішення: рестарт посеред спалаху втрачає memo, і поведінка відкочується до
сьогоднішньої — не гіршої за неї.

### Правило повноважень

**Memo може рівно те, що вже накладене стримання.** Це вісь усього дизайну, і
вона вже кодифікована в ядрі: `SENDER_REMOVAL_MIN_EVIDENCE = 2.0` відділяє
«прибрати повідомлення» від «прибрати людину».

| Уже застосовано на тригері | Що memo робить з наступними |
|---|---|
| `ban` / `kick` / `mute` — людину прибрали, планка 2.0 пройдена | видалити молча: нуль портів, нуль LLM, нуль нових суджень |
| `delete` — прибрали повідомлення, людина лишилась | судити як завжди; інцидент дає вагу (частина B) і переюзує картку |
| `needsVote` — сіра зона | інциденту немає; замість другого голосування доліплюємо повідомлення до наявного бюлетеня |
| `observe` / `captcha` / `none` | нічого (у капчі свій гейт `pendingCaptchas`) |

Інцидент відкривається лише коли `result.applied && isEnforcementAction(action)`
— тобто Telegram справді виконав дію.

### A. Короткий шлях і одна картка

Місце: `main.ts`, після блоку команд і **перед** `fireExtras` — відправник під
живим виносом не тригерить і хештег-утиліти.

Дефенс-ін-депс перед видаленням: `policy.trustedUserIds` (безкоштовно) та
`adminCache` (без сітьового виклику; промах кешу не блокує — інцидент за
побудовою існує лише для непривілейованого відправника, бо `applyVerdict`
відмовляє адмінам, собі й довіреним).

Записи: **один** запис у `pipeline_decisions` на інцидент. Перше повідомлення —
повний запис; наступні інкрементують `incidentCount` і додають `messageId` до
масиву. Новий метод `store.appendIncidentMessage(decisionId, messageId)`.

`adjustSpamMessages` — **раз на інцидент**, не на кожне memo-видалення. Інакше
лічильник детекцій надувається, а дві детекції забирають у акаунта весь
benefit of the doubt одразу.

Картка: `compactNotification` отримує `options.incidentCount`; при `count > 1`
рендерить «×N». Картка **редагується**, TTL автовидалення перезапускається.

Голосування: якщо для `(chatId, userId)` уже є відкритий бюлетень у вікні —
другий не відкривається; його прапорець-лічильник оновлюється.

### B. Спалах як доказ

Новий порт (`packages/core/src/ports.ts`):

```ts
interface BurstEntry { text: string; pSpam: number; hasMedia: boolean; at: number }
interface BurstPort {
  /** Вікно ДО поточного повідомлення — читається під час видобутку сигналів. */
  read(chatId: number, userId: number): Promise<BurstEntry[]>
  append(chatId: number, userId: number, entry: BurstEntry): Promise<void>
  reset(chatId: number, userId: number): Promise<void>
}
```

`read` і `append` розділені навмисно — інакше курка-і-яйце: сигнали потрібні до
скорингу, а `pSpam` поточного повідомлення відомий лише після. Тому пайплайн
**читає** вікно на стадії сигналів, а `main.ts` **дописує** запис уже після
вердикту — там само, де `conversationWindow.record`, і за тим самим правилом:
повідомлення, знесене memo, у вікно не потрапляє, бо його ніхто не судив.

Реалізація в Mongo (TTL 10 хв, cap 10 записів на ключ) — на відміну від memo, це
**створює вироки**, тому мусить бути відтворюваним у `tools/replay`.

Два сигнали, обидва `kind: 'shape'`:

| Сигнал | Умова | Вага (стартова) |
|---|---|---|
| `sender_burst` | ≥3 **різних** нормалізованих текстів у вікні | 0.8 |
| `burst_grey_repeat` | ≥2 записи вікна з `pSpam ≥ 0.35` | 1.0 |

`shape`, а не `evidence`, свідомо: `contentEvidence.total` живить планку 2.0, і
сигнал про *поведінку* не має права сам виносити людину. Це буквально урок
velocity — 16 % FP, після чого її знизили з вирішувача до сигналу.

«Різних» — обов'язкова умова. Однаковий текст світить `velocity_repeats` (1.5);
без цієї умови один факт рахувався б двічі, як уже було зі стеком новизни.
Обидва нові сигнали ділять одну групу `SIGNAL_GROUP_CAPS` — вони описують одну
й ту саму поведінку з двох боків.

Один виклик LLM на склеєний спалах — узагальнення `judgeAccumulated`. Тригер:
≥3 записи з реальним текстом і хоч один у сірій зоні (`pSpam ≥ LLM_GREY_LOW`),
за умови що поточне повідомлення не отримало вирішального вердикту раніше.
Наявна дисципліна зберігається повністю:

- `reset` після суду — інакше повертається «рулетка вироків»;
- `judgedText` / `judgedCount` / `llmModel` у мету;
- медіа рахуються для сигналу, але **не** їдуть у модель порожніми рядками
  (урок 2026-08-01: модель класифікувала `"\n\n\n\n"`);
- `capVouchedSession` застосовується й тут (перейменувати на `capVouchedWindow`);
- вердикт спалаху може `delete` + голосування; **виносити людину — лише за
  звичайною планкою 2.0**, бо окремо жоден рядок доказу не несе.

### C. Ретро-прибирання

Кільцевий буфер `Map<'chatId:userId', {messageId, at, pSpam}[]>`, 20 записів /
10 хв, у пам'яті — заповнюється для кожного судженого повідомлення.

Коли вердикт **виносить відправника** (`removesSender(action) && result.applied`)
— видаляємо забуферені повідомлення з `pSpam >= 0.35`. Планка ухвалена
користувачем 2026-08-20: це нижня межа сірої зони (`LLM_GREY_LOW`), тобто рівно
те, що пайплайн уже вважав нечистим. Звичайна балачка у сварці набирає ~0.1 і
залишається.

Незворотність. `restoreFalsePositive` уміє розбанити, зняти мут і повернути
standing, але відновити видалене не вміє. Сьогодні FP знищує одне повідомлення;
з C — до 20. Тому:

- `recordOverride` починає писати `removedCount` — скільки повідомлень знищив
  скасований вердикт. Без цього ціна помилки не рахується ніде.
- `restoreFalsePositive` стає інцидент-обізнаним: закриває інцидент, щоб memo не
  продовжувало виносити щойно виправданого відправника.

## Що це дає

| Метрика | До | Після |
|---|---|---|
| Виклики LLM на спалах з 8 повідомлень від забаненого | 8 | 1 |
| Карток у чаті | 8 | 1 («×8») |
| Записів у `pipeline_decisions` | 8 | 1 |
| Спам частинами (текст+фото+контакт) | не ловить ніщо | один виклик на склеєний спалах |
| Слід спамера після бану | перші N лишаються | видалені ті, що ≥ 0.35 |

## Верифікація

- Юніт-тести на кожну частину: таблиця повноважень memo (по рядку на дію),
  умова «різних текстів» для `sender_burst`, планка 0.35 для C.
- Property-тест: жодна послідовність повідомлень не призводить до видалення
  повідомлення з `pSpam < 0.35`, якщо відправника не виносили.
- Реплей (`tools/replay`) на прод-вердиктах: `BurstPort` має фейкову
  реалізацію, і нові сигнали не змінюють жодного наявного вердикту, окрім тих,
  де спалах справді був.
- Контрольний набір перед вмиканням B — за `docs/calibration.md`.

## Числа, які лишаються калібруванням

Стартові значення нижче — не виміряні; уточнюються реплеєм і продом.

| Параметр | Старт | Хто вирішує |
|---|---|---|
| TTL інциденту | 10 хв | виміряти розподілом інтервалів спалахів |
| Розмір буфера C | 20 / 10 хв | те саме |
| `sender_burst` K | 3 різних | реплей |
| Ваги `sender_burst` / `burst_grey_repeat` | 0.8 / 1.0 | контрольний набір |
| Планка C | **0.35** | ухвалено 2026-08-20 |
